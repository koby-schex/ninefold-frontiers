# Unit collection and progression interface

Use `MissionPresentation.Collection` to browse and change units on the same catalog-bound flow as mission preparation. Do not create another flow against the same files concurrently. This is an engine-independent interface; Unity screens, artwork, localization and touch layout are not rendered here.

`Read()` returns immutable faction groups, sorted by faction/unit ID. NPC templates are excluded. Each collectible shows ownership, Apex classification, current deployment stats and ability profiles, saved rank/customization, fragment balance, unlock cost, next advancement cost and blocking reasons. Unit and faction IDs remain content references, not invented display names. The existing fragment costs, rank caps and stat trade-offs are used without balance changes.

Unlock and advancement cards are informational: their offers cannot be confirmed directly. Call `Preview(operation, unitId, optionId)` to arm an explicit offer, then display its cost, balance, missing fragments, rank before/after and complete stat/ability before/after views. Customization options come from the unit's authored definition. Pass null as the customization option to reset. Current customization/reset costs are zero under the existing rules, and selecting the already active option is blocked as `NoChange` to avoid redundant ledger entries. Blocked offers can still show useful projections but must not enable a confirmation button. Unknown unit IDs or inappropriate option arguments throw and clear an old preview.

Call `Confirm(offer.Id)` with the exact displayed token. The controller consumes it before executing through `MissionFlow`, then returns immutable before/after progress only after the durable write succeeds. The token is also the underlying operation ID recorded in the corresponding unlock, advancement or customization receipt. A duplicate callback cannot spend again; a callback carrying an old token cannot confirm a replacement offer. `Cancel()` discards the current offer without writing. Reading or previewing never spends fragments or creates receipts.

Offers bind to both saved profile state and the in-memory battle checkpoint identity. Profile changes or reloads invalidate them; battle/results phases block all progression mutations. Collection browsing remains available during these phases, with blocked offers. A successful collection change also invalidates any previously displayed mission launch token, and refreshing preparation reflects new ownership/stats immediately. Stats use the same additive-over-base modifier and rounding functions as deployment; temporary combat statuses are excluded. Passive placeholders remain marked by the existing ability view.

On any save exception, no success result is returned. Honor the owning menu's `NeedsReload` and call `Open()` before proceeding. Do not automatically replay an old UI intent. A torn/failed write recovers the prior valid profile; a write whose acknowledgement was lost may already have committed. Reopening clears the pending offer and exposes the recovered ownership, rank, balances and durable receipt history. The player can create a new preview if the operation still makes sense. Failed reloads preserve files and remain blocked under the existing storage policy.

Tests cover grouping and exclusion of NPCs, fragment shortages, exact spending, inspected/deployed stat agreement, additive customization, reset, duplicate/replaced/unarmed confirmations, launch invalidation, battle/results restrictions, immutable views and both failed and ambiguous writes for all three operation types. This PR changes no canon, monetization, progression balance or save schema. All exercised content is the existing abstract fixture.
